# PHASE 2 — First Human-Labelled Search Benchmark

### Objective

Determine how good the existing retrieval system actually is.

This is the next major product milestone.

### 2.1 Approve the query catalogue

Review:

`data/evaluation/queries.example.json`

It currently contains 15 engineering queries across 15 topical areas.

Start with a three-query pilot using:

- `network-anomaly-lab`
- `crop-irrigation-advisor`
- `road-damage-vision`

The pilot is only for verifying the evaluation process. It is not the final benchmark.

Keep the original 15-query catalogue unchanged unless a reviewed update is necessary.

### 2.2 Capture real results

Use:

```
python scripts/capture_live_snapshot.py \
  data/evaluation/queries.example.json \
  --output data/evaluation/captures/run-YYYY-MM-DD.json
```

Use a new filename every time. The capture utility refuses to overwrite existing captures.

The current design captures up to:

- 25 OpenAlex candidates per query.
- 25 GitHub repository candidates per query.

For 15 queries, that is a theoretical maximum of 750 candidate records.

Actual counts will probably be lower.

**Quota consideration:** If using unauthenticated GitHub Search, be mindful of the 10-request-per-minute search limit. Use a free authenticated token stored locally or introduce request pacing before running a full capture. Never put that token in the frontend.

### 2.3 Export annotations

```
python scripts/export_live_annotations.py \
  data/evaluation/captures/run-YYYY-MM-DD.json \
  --output data/evaluation/annotations/run-YYYY-MM-DD.csv
```

The annotation sheet must remain neutral. It should not expose ranking scores or positions to reviewers.

### 2.4 Human grading

Use the existing 0–3 rubric:

| Grade | Interpretation        |
| ----- | --------------------- |
| 0     | Not relevant          |
| 1     | Weakly related        |
| 2     | Substantially related |
| 3     | Highly relevant       |

Every candidate must receive an explicit grade.

Do not leave blanks for candidates believed to be irrelevant. Use grade 0.

Record a short rationale and confidence level.

For team-based evaluation, assign a primary reviewer to each candidate and have another reviewer independently assess a sample. Record disagreements separately; the current annotation schema does not automatically identify multiple reviewers.

### 2.5 Build the reviewed snapshot

```
python scripts/build_reviewed_snapshot.py \
  data/evaluation/captures/run-YYYY-MM-DD.json \
  data/evaluation/annotations/run-YYYY-MM-DD.csv \
  --output data/evaluation/reviewed/run-YYYY-MM-DD.json
```

The builder rejects incomplete or inconsistent annotations.

### 2.6 Generate the evaluation report

```
python scripts/evaluate_live_search.py \
  data/evaluation/reviewed/run-YYYY-MM-DD.json
```

Also run the BM25-only mode:

```
python scripts/evaluate_live_search.py \
  data/evaluation/reviewed/run-YYYY-MM-DD.json \
  --bm25-only
```

Compare:

- Provider-native ranking.
- BM25.
- BGE dense retrieval.
- Hybrid RRF.

Metrics:

- Precision\@5.
- Recall\@10.
- nDCG\@10.
- MRR\@10.

### Interpretation rules

- Empty provider response is not the same as a failed provider.
- Provider failure is not a collection of irrelevant results.
- No positive labels means meaningful relevance metrics cannot be calculated.
- If BGE fails, do not report BM25 fallback as dense retrieval.
- The benchmark measures candidates discovered in the captured pool, not every relevant project on the internet.

### Completion condition

The first reviewed benchmark report exists, is reproducible and contains no automatically generated relevance labels.

# PHASE 3 — GitHub Discovery Quality Improvement

### Objective

Improve the number and relevance of repositories discovered by GitHub Search.

### Existing issue

The current GitHub adapter sends almost the entire idea sentence as a single search query.

This can cause poor retrieval and can exceed GitHub's documented search-query length limit discussed in the earlier code review.

### 3.1 Preserve the current implementation as baseline

Before changing anything:

- Keep the existing search-query behaviour.
- Capture baseline results.
- Record candidate counts and provider states.
- Do not modify BM25, BGE or RRF.

### 3.2 Build deterministic query extraction

Create a local query-construction component.

It should identify and preserve:

- Main problem or application domain.
- Relevant hardware.
- Programming languages and frameworks.
- Technical approaches.
- Named algorithms, models and protocols.
- Important acronyms.

It should remove unnecessary conversational words such as "I want to build", "create a system", and "develop a solution".

Example:

Input:

> Build a low-cost system that combines vibration and temperature sensors to identify early signs of failure in small factory motors and notify maintenance staff.

Possible compact query:

`motor predictive maintenance vibration temperature sensors`

This is an experiment, not a guaranteed improvement.

### 3.3 Implement query validation

The generated GitHub search text must:

- Stay comfortably below the documented query limit.
- Exclude unsupported or malformed syntax.
- Keep important technical terms intact.
- Preserve the original idea separately.
- Avoid silently dropping critical concepts.

Keep the GitHub API qualifiers separate from the generated keyword text.

### 3.4 Compare search strategies

Evaluate:

A. Original full-sentence query.

B. Compact extracted keyword query.

C. A compact phrase retaining the main application and technologies.

Use the same idea catalogue and similar capture conditions.

### Important evaluation gap

The existing evaluation system compares ranking methods over one captured candidate pool. It does not, by itself, prove that a new query strategy discovered more relevant candidates.

Therefore, add a discovery comparison workflow that:

1. Preserves the candidate pools from both strategies.
2. Identifies common candidates.
3. Identifies candidates unique to either strategy.
4. Combines candidates into a reviewed union for human grading.
5. Measures relevant candidates discovered by each strategy.
6. Records API failures and provider quotas separately.

Do not compare only raw result counts. More results do not necessarily mean better discovery.

### Completion condition

The new GitHub query strategy demonstrates measurable improvements against the baseline without sacrificing important relevant results.

# PHASE 5 — Backend Reliability and API Protection

### Objective

Make Live Research dependable when multiple users submit ideas.

### Implement the following

**1. Caching**

Cache normalized provider responses.

Suggested starting policy:

- GitHub repository results: short configurable TTL.
- OpenAlex research records: longer configurable TTL.
- Include normalized query, provider, adapter version and relevant configuration in the cache key.

Avoid serving the same query to multiple concurrent requests by making duplicate in-flight requests share the same provider operation.

A local SQLite-backed cache is a reasonable initial no-cost option for a single-instance deployment.

**2. Rate limiting**

Implement:

- Per-client request limits.
- Global provider request budgets.
- Protection against rapid repeated submissions.
- A maximum number of concurrent provider calls.

Do not trust arbitrary client-supplied `X-Forwarded-For` headers. Only use forwarded client information from a trusted proxy configuration.

**3. Error and retry handling**

- Respect `Retry-After`.
- Use bounded exponential backoff with jitter for transient failures.
- Do not repeatedly retry invalid requests or invalid credentials.
- Keep provider states distinguishable.
- Preserve partial success.

**4. Health endpoint**

Introduce `/health` with a small, stable response.

Distinguish application availability from the availability of external providers.

**5. Structured logs**

Include:

- Request ID.
- Endpoint.
- Provider status.
- Provider latency.
- Cache hit/miss.
- Error category.
- Ranking mode.

Do not log the full submitted project idea by default.

**6. Privacy disclosure**

Before Live Research submission, communicate that the idea is sent to OpenAlex and GitHub for search.

Do not promise that submitted data is never stored unless that has been verified.

### Completion condition

The backend protects shared API quotas, reports failures correctly and handles repeat requests efficiently.

# PHASE 7 — Startup Performance and Local Index Management

### Objective

Avoid unnecessary model loading and vector-index rebuilding.

### Tasks

1. Inspect the ChromaDB initialization and collection lifecycle.
2. Determine why and when the existing code rebuilds the index.
3. Define an index fingerprint using:
   - Dataset content hash.
   - Embedding model identifier.
   - Embedding dimension.
   - Index schema version.
4. Reuse the existing index when its fingerprint matches.
5. Rebuild only when the dataset or model configuration changes.
6. Avoid deleting an existing valid index before the replacement is successfully built.
7. Test interrupted index creation.
8. Test application restart and recovery.
9. Keep the live-search model configuration separate from offline search configuration.

### Failure scenarios

- BGE cannot download: use explicitly labelled BM25-only degraded mode.
- CUDA out of memory: retry with CPU or smaller embedding batches.
- Index is incomplete: verify its fingerprint and rebuild safely.
- Dataset changed: invalidate the old index through a controlled rebuild.
- Model version changed: rebuild embeddings; do not silently mix model versions.

### Completion condition

Repeated server restarts do not unnecessarily rebuild a valid local index.

# 6. Error and exception handling reference

| Error / situation                            | Likely reason                                      | Correct response                                                         |
| -------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| `ModuleNotFoundError`                        | Wrong interpreter or missing dependencies          | Activate `.venv` and install requirements                                |
| Python version mismatch                      | Unsupported environment                            | Use the documented Python version                                        |
| `pip install` failure                        | Network, package compatibility or platform issue   | Inspect exact package failure; install individually only when diagnosing |
| Port 8000 occupied                           | Existing API process                               | Stop the process or use another port and update config                   |
| Frontend port unavailable                    | Existing HTTP server                               | Use another port and ensure CORS permits that exact origin               |
| CORS error                                   | Wrong or missing origin                            | Check exact frontend origin in backend configuration                     |
| Frontend sends to localhost after deployment | Default API configuration was not replaced         | Set public HTTPS API origin                                              |
| OpenAlex timeout                             | Network or provider issue                          | Bounded retry; preserve failure state                                    |
| OpenAlex `429`                               | Request-rate or daily-budget limit                 | Respect response headers and stop repeated attempts                      |
| GitHub `401`                                 | Invalid or missing authentication where required   | Check server-side token configuration                                    |
| GitHub `403`                                 | Permission, primary quota or secondary quota issue | Inspect response headers and message before retrying                     |
| GitHub `422`                                 | Invalid or overly long search query                | Validate and compact the query; don't retry unchanged input              |
| GitHub `429`                                 | Search-specific rate limit                         | Honor `Retry-After` and reduce request frequency                         |
| One provider fails                           | External provider unavailable                      | Return valid partial results                                             |
| Both providers fail                          | Neither external source is available               | Return unavailable, not an empty success                                 |
| No candidates found                          | Successful provider search returned zero items     | Show an actual empty-result state                                        |
| BGE download failure                         | Network or model-host availability                 | Use explicit BM25-only degraded mode                                     |
| BGE out of memory                            | Insufficient memory for current configuration      | Use CPU or smaller batches                                               |
| ChromaDB index mismatch                      | Dataset/model/schema changed                       | Rebuild safely using a verified fingerprint                              |
| Capture filename exists                      | Protection against overwriting data                | Choose a unique filename                                                 |
| CSV annotations incomplete                   | Some candidates were not reviewed                  | Complete every row; use explicit grade 0                                 |
| Duplicate candidate annotations              | Accidental duplicated rows                         | Resolve duplicates before snapshot creation                              |
| Query changed after capture                  | Catalogue no longer matches captured data          | Create a new capture for the revised catalogue                           |
| No positive relevance labels                 | Query has no reviewed relevant candidates          | Keep case visible but exclude invalid aggregate calculations             |
| Evaluation output missing dense metrics      | Embedding process failed                           | Report the dense failure; do not mislabel BM25 fallback                  |
| Git accidentally tracks evaluation captures  | `.gitignore` mistake or forced add                 | Inspect `git status`; remove sensitive generated data from staging       |
| GitHub Actions fails installing packages     | Runner or dependency incompatibility               | Inspect installation logs and reproduce locally                          |
| GitHub Actions passes but BGE fails locally  | CI didn't download/load the real model             | Run the separate local model smoke test                                  |
| Tailwind styles disappear offline            | CDN unavailable                                    | Use built CSS                                                            |
| Shared provider quota is exhausted           | Too many users/searches                            | Use caching, rate limits and quota monitoring                            |

## 5. A practical error-handling strategy for the project

The roadmap contains a full error matrix, but I want to highlight five cases that are especially important for Idea Enhancer.

Case A — GitHub is unavailable, OpenAlex works

Expected behaviour: partial results

Keep the academic paper results, mark GitHub unavailable and allow the user to retry later. Do not present this as a successful two-provider search.

Case B — OpenAlex works, GitHub returns HTTP 422

Expected behaviour: query/provider error

Inspect the constructed GitHub query. Do not blindly retry the same malformed or overlong query.

Case C — BGE cannot load

Expected behaviour: degraded search

Continue using BM25 when permitted by the existing design. Clearly identify that dense and hybrid evaluation was unavailable.

Case D — Evaluation has no relevant candidates

Expected behaviour: no unsupported conclusion

Keep the case visible, inspect the discovery process and avoid claiming that the idea has no prior art.

Case E — An AI assistant disappears or reaches its quota

Expected behaviour: development continues

Read the issue, inspect the relevant files, implement a small change, run tests and commit it. No application functionality should be affected.
